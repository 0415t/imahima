# グループチャットMVP：現在のバックエンド

## 構成

Expressの4 APIは`server/chat.ts`、RPCへの接続は`server/services/chat.ts`を参照。JWTから確定したactorだけを使用し、所属をAPIとRPCで確認する。送信・履歴・削除・変更イベント取得を提供する。一般JWTに本文テーブルや管理RPCの直接操作権限は与えない。

`server/auth.ts`は無効・期限切れ認証を401、上流障害・不明な認証エラーを503に分類する。`server/timeouts.ts`はAuth 5秒、PostgREST通信1試行8秒、グループ系HTTP全体20秒を設定する。HTTP終了はDB処理の取消しを保証しない。同じ`client_message_id`で再送する。

## データ・アーカイブ

グループ管理、チャット、管理フラグの順にマイグレーションを適用する。既存マイグレーションは編集しない。最新の管理フラグ移行には、事前承認した既存roomの分類が必要であり、未知のroomは推測で分類しない。ローカル分類manifestはGit対象外。

`mvp_managed`は作成者参照から独立し、新規MVP roomではtrue。所属DELETEまたはroom移動の後、DBトリガーが旧roomをロックし、管理対象かつ未アーカイブで所属0人ならアーカイブする。Auth hard deleteのCASCADEにも適用される。非MVP roomは自動アーカイブしない。既存履歴・所属・招待コードの物理削除は行わない。

チャットはroom内採番、ユーザー単位の全room合計10件/直近60秒、冪等送信をRPCで処理する。削除済みメッセージも制限に含む。論理削除では本文をNULLにし、再送で復元しない。イベントは本文・本文ハッシュを含まない。アカウント削除時の送信者参照・履歴保存はチャットmigrationのFKに従う。

## Realtimeの受入条件

- channel接続そのものの拒否は必須ではない。
- RLSによる不正なデータ取得拒否、退出・アーカイブ後の不正な新規配送拒否は必須。
- 通常の`SUBSCRIBED`とPostgres Changesの準備完了は区別する。検証SDKの`postgres_changes_options.wait: true`で準備完了を待つ。
- Realtimeは永続配送保証として扱わず、初期化・再接続・JWT更新・復帰時のREST差分同期を必須にする。イベントIDで重複を排除し、ページ内固定high-waterと継続カーソルを尊重する。
- 修復済みの歴史的roomに対する新規イベント配送試験は未実施。別の新規アーカイブfixtureにおける配送拒否試験とは区別する。

## 記録と制約

[検証手順](group-chat-verification.md)を現在の入口にする。`*.public.md`は匿名化した過去の設計・検証記録であり、過去の失敗や未実施事項を保持する。元の記録はローカルに保持する。

単発25秒クライアントタイムアウト、初回Realtime購読失敗の原因未確定記録は維持する。20秒HTTP期限の独立検証成功を、その原因が修正済みである証拠とはしない。実タイマー更新・延長の結合試験は、このローカルスキーマに実関数がないため未実施。フロントエンド・Pushは今回の変更対象外。
